# Dematus 3.0

Dematus - локальный инструмент для анализа драфтов в Dota 2. До старта игры он сравнивает силу драфта Radiant и Dire на базе данных STRATZ, сохраняет расчёт и выгружает ключевые значения в Google Sheets. Цель проекта - находить ситуации, где оценка Dematus заметно расходится с коэффициентом букмекера, и со временем построить на накопленных данных ML-модель.

## Что уже сделано

### Единая запись каждого расчёта: snapshot

Каждый запуск Dematus теперь создаёт **snapshot** - сохранённый снимок того, что система знала в момент прогноза. Это основа для честного анализа и будущего обучения модели.

Snapshot хранит:

- источник расчёта: live из DLTV extension, Match ID или ручной ввод;
- время расчёта;
- команды, турнир, Match ID и ссылку DLTV, если они известны;
- драфты обеих сторон;
- сырые ответы STRATZ;
- рассчитанные признаки и итог текущей формулы;
- данные, отправленные в Google Sheets;
- введённые коэффициенты букмекера, если они есть;
- результат матча, когда он будет добавлен;
- версию модели/формулы.

Зачем это нужно: STRATZ обновляет агрегированные показатели со временем. Без snapshot старый прогноз невозможно честно воспроизвести - тот же драфт позже мог бы получить другие цифры. Snapshot фиксирует именно ту информацию, на которой был основан прогноз в момент его создания.

Основное хранилище теперь - локальная база Dematus. Google Sheets остаётся удобной витриной и местом для ручной работы, но не единственным источником данных.

### Два рабочих способа расчёта

1. **Live через DLTV extension.** Расширение собирает текущий драфт с DLTV и отправляет его в локальный Dematus в один клик. Создаётся snapshot, выполняется расчёт и строка уходит в Google Sheets.
2. **По Match ID.** Dematus получает контекст уже существующего матча из STRATZ, выполняет тот же расчёт, сохраняет snapshot и отправляет данные в таблицу. Этот режим удобен для проверки и исторического анализа, но его нельзя выдавать за чистый live-бэктест, если расчёт был сделан после окончания матча.

Оба режима используют одну и ту же основную цепочку расчёта. В live-режиме Match ID и итог матча могут быть неизвестны на момент драфта - это нормально.

### Окна данных STRATZ: 4w / 8w / 12w

Помимо базового ответа STRATZ, для каждого snapshot можно собрать три временных окна:

| Окно | Что означает |
| --- | --- |
| `4w` | агрегированные данные за последние 4 недели на момент snapshot |
| `8w` | агрегированные данные за последние 8 недель на момент snapshot |
| `12w` | агрегированные данные за последние 12 недель на момент snapshot |

Базовая рабочая гипотеза - использовать 12 недель как основной горизонт, пока патч не меняется. За выходом новых патчей нужно следить вручную: после значительного изменения патча старые недели не стоит механически смешивать с новыми.

Система забирает 12 недель одним проходом и из них формирует 4w, 8w и 12w. Это уменьшает число обращений к STRATZ и не создаёт дублей при повторном нажатии: уже собранные полные окна повторно не загружаются.

Важно различать:

- `weekOffset = 0` в технических данных означает текущую, самую свежую неделю, а не «ноль недель данных»;
- `4w`, `8w`, `12w` - это полноценные накопленные окна из 4, 8 и 12 недель.

В старой логике часть показателей имела разную глубину: winrate героя мог браться за 1 неделю, а синергия - за 4. Теперь эта разница явно видна в сохранённых данных, а новые окна дают основу, чтобы позже сравнить варианты честно и выбрать их на данных, а не вручную.

### Экспорт набора данных для анализа

В интерфейсе snapshot есть действие **Export Dataset**. Оно создаёт или обновляет лист `Dataset` в той же Google-таблице.

В `Dataset` выгружаются не огромные JSON-ответы, а плоские числовые признаки, например:

- средний winrate героев Radiant и Dire;
- число матчей в выборке;
- синергия внутри каждой команды и её разница;
- преимущество по матчапам;
- показатели темпа на 20-й и 60-й минутах;
- идентификатор snapshot, источник, время и Match ID;
- вручную введённые коэффициенты букмекера Radiant и Dire;
- результат матча, когда он добавлен.

Ручными на данном этапе оставлены только букмекерские коэффициенты. Поля `bookmaker_source` и `bookmaker_captured_at` намеренно убраны, чтобы не сдвигать существующие столбцы в рабочей таблице.

Google Sheets можно использовать как удобную промежуточную таблицу для просмотра и ручного внесения коэффициентов. Для обучения ML в дальнейшем правильнее брать тот же набор из локальной базы или выгружать его в CSV: так данные будут стабильнее и полнее.

## Где что хранится

| Что | Где находится |
| --- | --- |
| Код и локальная база Dematus | эта папка проекта |
| Snapshot и окна STRATZ | локальная база Dematus |
| Сырые ответы STRATZ | внутри snapshot и окон данных в локальной базе |
| Отображение live-результатов | Google Sheets, лист `Dematus 3.0` |
| Плоский набор признаков | Google Sheets, лист `Dataset` |
| Настройки и секреты | локальный `.env` (не передавать другим людям) |
| Доступ Dematus к Google Sheets | `storage/app/google-sheets-service-account.json` (не публиковать) |

Объём данных будет расти, потому что сохраняются сырые ответы STRATZ. Для обычной дистанции в сотни и тысячи расчётов это нормально для локального компьютера. При заметном росте базы позже можно будет настроить архивирование и хранить старые тяжёлые ответы отдельно, не теряя плоский датасет.

## Как запускать Dematus

1. Дважды нажать `start-dematus.bat` в корне этой папки.
2. Оставить открытым окно Dematus: оно запускает backend и фоновый обработчик очереди импорта. Пока оно открыто, локальная система работает.
3. Открыть в браузере `http://127.0.0.1:8000`.
4. После работы закрыть эти окна или запустить `stop-dematus.bat`.

Обычно вручную нужны только `start-dematus.bat` и команда `start-dematus.bat stop`. Backend и обработчик очереди работают в фоне, а их журналы сохраняются в `storage/logs/`.

## Важные ограничения и защита от data leakage

**Data leakage** - это ситуация, когда в прогноз случайно попадает информация из будущего. Тогда бэктест выглядит лучше реальности, но live-результат не повторяется.

Чтобы этого избежать:

- для оценки качества использовать snapshot, созданные до начала игры;
- привязывать окна 4w/8w/12w к времени `captured_at`, а не получать текущие показатели STRATZ задним числом;
- не использовать итог матча или любые послематчевые показатели как входы модели;
- разделять live-данные и расчёты по завершённому Match ID при анализе качества;
- обучать и проверять модель по времени: сначала старые матчи, затем более новые, а не случайно перемешивать весь набор.

Одна из исходных проблем Dematus как раз состояла в том, что готовые агрегаты STRATZ меняются со временем. Snapshot и зафиксированные временные окна не отменяют изменения STRATZ, но позволяют точно знать, на каких данных был построен каждый прогноз, и перестать подменять историческую информацию сегодняшней.

## Что пока не меняли

- Основную математическую формулу Dematus пока не переписывали.
- ML-модель пока не подключали.
- Функционал по отдельным про-игрокам не является частью текущего плана; на одном патче для него слишком мало устойчивых данных.
- Автоматического получения букмекерских коэффициентов пока нет: их вводят вручную.

Это сознательно: сначала нужно накопить чистые live-snapshot с зафиксированными входными данными и результатами, затем измерить качество текущей формулы. Переписывать формулу до этого означало бы менять систему без надёжного способа доказать, что она стала лучше.

## Ближайший план

1. Добавить простую проверку готовности датасета: есть ли необходимые столбцы, результаты матчей, букмекерские коэффициенты и собранные 4w/8w/12w.
2. Сделать удобное добавление фактического результата матча к завершённому snapshot.
3. Собрать больше именно live-расчётов на нескольких турнирах, регулярно заполняя коэффициенты и итоги матчей.
4. Проверить текущую формулу: калибровку вероятностей, ROI, влияние размера edge, работу фаворитов и андердогов, разницу 4w/8w/12w.
5. После накопления данных запустить первую простую ML-модель: использовать букмекерский коэффициент как рыночную базовую оценку и признаки Dematus как возможную поправку к ней.
6. Только после сравнения с понятным baseline решить, как менять итоговую формулу и пороги ставок.

Для первых осмысленных выводов нужны не десятки игр, а хотя бы сотни чистых live-наблюдений. Для устойчивой ML-проверки желательно стремиться к тысячам матчей, особенно если хочется отдельно анализировать разные размеры коэффициентов, турниры и патчи.
